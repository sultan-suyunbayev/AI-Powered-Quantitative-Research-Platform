Design Doc: CCEA — Cloud Research + Deploy-to-Agent + Local Live Execution + Cloud Control/Monitoring
1) Контекст и цель
1.1 Контекст

Мы строим SaaS-платформу для:

разработки стратегий (включая AI/RL),

бэктеста и реалистичной симуляции исполнения,

управления версиями стратегий/моделей,

мониторинга live-запусков.

Ключевое: live-исполнение ордеров не происходит в облаке. Оно происходит в среде клиента:

локальный Agent на машине пользователя / VPS пользователя (BYO host),

или on-prem / VPC клиента (enterprise).

1.2 Цель

Сделать архитектуру, которая:

Технически обеспечивает нормальный UX “автоторговли”, но без того, чтобы cloud становился execution-service.

Юридически/коммерчески позиционируется как “software provider”, снижая риски квалификации как RTO/execution/advice.

Designed for enterprise use: auditability, change control, data governance, vendor pack.

1.3 Короткая формула CCEA

Cloud: research, симуляция, сборка/подпись артефактов, мониторинг, lifecycle-requests.

Agent: ключи, live decision loop, риск-контроли, формирование и отправка ордеров, локальные approve.

2) Термины

Cloud — наши SaaS сервисы.

Agent — клиентский runtime (daemon) в среде клиента.

Strategy — пользовательский код/модель, выдающая Intent.

Intent — высокоуровневое намерение (target exposure/позиция/действие), не “готовый ордер”.

Order — конкретный приказ брокеру (создаётся только в Agent).

Deployment — связь артефакта стратегии + конфигурации + целевого агента.

Run — конкретный запуск стратегии на агенте.

Command — lifecycle запрос от Cloud к Agent.

Approval — локальное подтверждение торгово-значимого изменения на Agent.

TRADING_IMPACTING — класс изменения, влияющий на торговое поведение.

NON_IMPACTING — изменение, не влияющее на торговое поведение (логирование, UI, telemetry verbosity и т.п.).

3) Требования
3.1 Must-have (обязательное)

Cloud не хранит секреты (API keys) и не вызывает торговые API брокеров/бирж.

Cloud не генерирует/не передаёт live-торговые инструкции (orders/targets/signals для live).

Agent — единственная зона, где:

хранятся ключи,

создаются/отправляются ордера,

применяется enforcement риск-политики,

живёт kill switch.

Любые TRADING_IMPACTING изменения требуют локального approve на Agent (по умолчанию).

Артефакты стратегий:

immutable (digest pinned),

signed (Agent проверяет),

с manifest + SBOM.

Протокол Agent↔Cloud:

outbound connection от Agent (без inbound дыр в инфраструктуре клиента),

idempotent команды,

audit trail.

Надёжность:

reconciliation позиций/ордеров,

safe-degraded режимы (cloud down / network down),

журналирование.

Privacy/GDPR:

минимизация телеметрии,

уровни чувствительности данных,

retention и удаление,

EU data residency по умолчанию для EU клиентов.

Enterprise:

режим on-prem/VPC,

экспорт evidence pack,

change management и access audit.

3.2 Should-have (желательно)

Локальные политики авто-approve с белыми списками (workspace/strategy/instruments).

Агрегированная телеметрия по умолчанию, raw order events — опционально.

Версионирование схем сообщений.

Пиннинг версий Agent в enterprise (change windows).

“Break-glass” доступ к чувствительным данным (строго аудируемый).

3.3 Non-goals (не делаем в этой итерации)

Managed hosting агента нами (это отдельный продуктовый режим и отдельный legal review).

Copy-trading / соц-торговля / “лидеры сигналов” (там сразу тяжёлые вопросы по advice/портфельному управлению).

Гарантии доходности, “best execution” как обещание (мы не брокер и не venue).

Любые “облачные” брокерские интеграции с ключами пользователя.

5) Слои ответственности (очень важно)
5.1 Где рождается торговое решение

Live Intent рождается только на Agent (в runtime стратегии).

Cloud может хранить research-результаты, но не передаёт live-targets.

5.2 Кто может “запустить торговлю”

Cloud отправляет только REQUEST_START.

Agent по умолчанию требует локальный approve или заранее настроенную локальную политику авто-approve.

5.3 Кто может изменить торговое поведение

Любые TRADING_IMPACTING изменения:

стратегия/модель/версия артефакта,

universe инструментов,

параметры execution (order types, aggressiveness),

риск-лимиты,

расписание live,

переключение paper→live,

брокер-аккаунт/адаптер,
— только через локальное подтверждение (или локальный auto-approve policy).

5.4 Что Cloud может делать без approve

Stop/Pause (safety, снижает риск)

Non-impacting изменения (например telemetry verbosity, log level)

7) Классификация изменений: TRADING_IMPACTING vs NON_IMPACTING
7.1 TRADING_IMPACTING (требует локального approve)

Новый build/версия стратегии или модели

Переключение PAPER↔LIVE

Изменение universe инструментов

Изменение риск-лимитов (любое ослабление; ужесточение можно разрешать без approve только если локальная политика это разрешает, но проще: всё через approve)

Изменение брокер-адаптера/аккаунта

Изменение execution-параметров:

order types

time-in-force

агрессивность/пороговые условия

max order rate

Изменение расписания live (если влияет на торговые сессии)

Изменение параметров стратегии, влияющих на сигналы/входы/выходы

7.2 NON_IMPACTING (может применяться без approve)

Уровень логирования

Telemetry verbosity (если не добавляет чувствительные поля)

UI/UX параметры

Non-functional конфиги раннера (например размер буфера)

Обновление агента (в retail можно auto-update, в enterprise — по change window; но это отдельная политика)

7.3 Policy Firewall (локальные “hard caps”)

Agent хранит локальную политику, которая:

задаёт абсолютные верхние границы риска

запрещает некоторые инструменты/типы ордеров

запрещает авто-approve для некоторых изменений

Cloud не может “поднять” риск выше hard caps никогда.

9) Agent: runtime, sandbox, secrets, enforcement
9.1 Secrets (Local Vault)

Требования:

Секреты хранятся только локально.

В логах/телеметрии секреты не появляются (редакция).

Ротация ключей — локальная операция.

Поддержка нескольких broker accounts (с явным выбором, но без cloud доступа к ключам).

9.2 Sandbox

Базово:

стратегия запускается в отдельном процессе/контейнере

лимиты CPU/RAM
Enterprise:

egress allowlist

read-only FS

запрет произвольных исходящих запросов

9.3 Live Loop: где создаётся Order

Пайплайн:

Market snapshot

Strategy → Intent

Risk Manager (локально) → Allowed Actions

Execution Engine → Orders

Broker Connector → send orders

Cloud не участвует ни на одном из шагов 1–5.

9.4 Kill Switch

Триггеры (минимум):

max daily loss

broker errors burst

latency spike

order spam

state divergence

data feed invalid

Действия:

cancel open orders

optional flatten (только если локально разрешено)

halt run

9.5 Reconciliation / Idempotency

Требования:

Каждый ордер имеет client_order_id (deterministic/idempotent)

При рестарте:

fetch open orders, positions

reconcile local journal

if uncertain → safe halt

Никаких “дублирующих” ордеров из-за retries.

10) Протокол Agent↔Cloud (Control Plane + Telemetry)
10.1 Транспорт

Принцип: Agent делает outbound соединение.
Варианты:

HTTPS long-poll (просто, надёжно)

WebSocket (если нужен realtime)

gRPC over TLS (enterprise)

На старте — long-poll + отдельный endpoint для telemetry ingestion.

10.2 Аутентификация

Enrollment token (одноразовый, TTL)

После enrollment: agent использует device key + signed JWT или mTLS.

Каждое сообщение подписано/аутентифицировано.

10.3 Версионирование

Все сообщения имеют schema_version.

Agent и Cloud договариваются о min_supported / max_supported.

В протоколе не существует:

любых payload, которые содержат price/qty/side как “готовый ордер” для live.

Это фиксируется:

в JSON schema,

в CI guardrails,

в code review policy.

11) State Machine: Deployment и Run
11.1 Deployment state (Cloud-логика + репорты от Agent)

Состояния:

CREATED — создан деплой

REQUESTED_START — отправлен request start

PENDING_LOCAL_APPROVAL — ожидаем локального approve

APPROVED — approve получен

ACTIVE — run запущен

PAUSED — пауза

REQUESTED_STOP — запрос стоп

STOPPED — остановлен

HALTED — аварийная остановка (kill switch)

REVOKED — агент/ключ отозван

ARCHIVED — архив

Переходы:

CREATED → REQUESTED_START (user presses Deploy/Start)

REQUESTED_START → PENDING_LOCAL_APPROVAL (если requires_approval)

PENDING_LOCAL_APPROVAL → APPROVED (agent approval)

APPROVED → ACTIVE (agent applied)

ACTIVE → PAUSED (pause request)

ACTIVE → REQUESTED_STOP → STOPPED

ACTIVE → HALTED (local kill switch)

ANY → REVOKED (security revoke)

11.2 Run state (на Agent, репортится в Cloud)

INIT

STARTING

RUNNING

DEGRADED (необязательное, если хочешь явный режим)

PAUSED

STOPPING

STOPPED

HALTED

FAILED (неожиданная ошибка, без гарантий корректного стопа)

12) Конфигурация: layering и immutable blobs
12.1 Слои конфигурации

Cloud deployment config (immutable blob): без секретов

Agent local policy (hard caps + approve rules): всегда приоритет

Broker credentials (local vault): только локально

Runtime state (positions/orders): только локально, но может агрегировано телеметриться

12.2 Immutable config blobs

Cloud хранит config как blob с digest:

любые изменения создают новый blob

команды ссылаются на digest

Agent может показывать diff при approve

13) Telemetry: уровни чувствительности и дефолты
13.1 Уровни

AGGREGATED (default): PnL, drawdown, exposure, error rates, health

DETAILED_NON_SENSITIVE: таймстемпы, latency, но без конкретных ордеров

RAW_ORDER_EVENTS (opt-in): order/fill события (опасно для privacy и IP)

13.2 Дефолты

Retail: AGGREGATED

Pro: AGGREGATED + выборочные технические метрики

Enterprise: конфигурируемо, часто “telemetry stays local” или выборочный экспорт

13.3 Redaction

Перед отправкой telemetry:

вычищать секреты

маскировать идентификаторы аккаунтов

запрещать логирование env vars

14) Privacy/GDPR и Data Residency
14.1 Data minimization

мониторинга

14.3 EU residency

14.4 Access control

18) ToS / Marketing / AUP / IP — как часть дизайна
18.1 ToS (публичные)

0) Базовые принципы, роли, и “границы периметра” (цемент)
0.1 “Ключи локально” — сильный аргумент, но не гарантия

Локальные ключи + локальная отправка ордеров сильно снижают риск квалификации как услуги (RTO/execution), но не дают иммунитет, если по сути:

вы контролируете торговые решения/параметры;

у пользователя нет реального контроля (включая auto-start/auto-upgrade без локального approve);

маркетинг продаёт “мы торгуем за вас”;

вы фактически оказываете “order routing / execution as a service”.

Следствие: архитектура + договоры + маркетинг должны говорить одно и то же.

0.2 Cloud-платформа (SaaS) — список “запрещено навсегда”

Cloud никогда не должен:

хранить API-ключи пользователя (ни в БД, ни в логах, ни в support dumps);

иметь сетевой доступ/код, который обращается к брокерским/биржевым торговым API от имени пользователя;

формировать/передавать live торговые инструкции/ордера/targets/“готовые сделки”;

содержать control-plane команду или payload, который можно интерпретировать как PLACE_ORDER / SUBMIT_ORDER.

Техническое требование: в cloud-контейнерах/пакетах вообще не должно быть модулей “live order submitter / broker trading client”.

0.3 Agent (local/VPS/on-prem) — единственная зона исполнения

Agent у пользователя/клиента:

хранит секреты локально;

держит соединение с брокером;

локально генерирует intent и превращает intent в ордера;

отправляет ордера;

применяет риск-контроли, kill switch, reconciliation;

пишет локальный журнал (для восстановления/разборов).

0.4 “Agent у пользователя” ≠ “managed agent by you”

В базовой модели:

BYO host: домашняя машина пользователя или VPS, который пользователь арендует и админит;

или enterprise on-prem/VPC клиента.

Любой “мы вам хостим agent” — это отдельный продуктовый режим с отдельной юридической оценкой (и, честно, быстро приближает к модели execution service).

0.5 Control plane: “lifecycle” ≠ “trading control”

Любая удалённая кнопка, которая меняет торговое поведение, может выглядеть как управление торговлей. Поэтому:

cloud отправляет REQUEST на старт/апгрейд/изменения, а agent применяет только после локального approve (по умолчанию);

stop/pause можно делать удалённо (это safety feature);

“flatten позиции” по умолчанию не делается удалённо (только локально/enterprise-режим по договору).

0.6 Риск “investment advice” (даже без исполнения)

Если платформа выдаёт персональные рекомендации (“это подходит именно вам”), вы можете попасть в периметр “investment advice”. Поэтому:

cloud-отчёты формулируются как research/metrics, не как персональные советы;

не собирать у retail пользователя “обстоятельства” так, чтобы выходило suitability;

“signals” в UI позиционировать как выход пользовательской стратегии, а не “совет платформы”.

0.7 Три режима продукта (чтобы не убить себя регуляторкой и не развалить GTM)

Retail Research SaaS (EU-friendly): IDE/ноутбуки/бэктест/сим/мониторинг + агент BYO (опционально).

Retail Live via Local Agent (BYO host): автоисполнение локально, cloud — наблюдаемость и lifecycle requests.

Enterprise Engine (on-prem/VPC/self-hosted): execution внутри инфраструктуры клиента + DORA/аудит/контрактные пакеты.

1) Компоненты (сервисы) и разбиение на зоны
Cloud (SaaS) — “Research + Artifact + Control plane + Observability + Governance”

Сервисы:

Auth/Accounts

пользователи, организации, workspace, роли, MFA, аудит доступа.

Strategy Workspace

IDE/ноутбуки, репозиторий стратегий, версии, эксперименты, артефакты.

Backtest & Sim Service

backtest jobs, симуляция исполнения (fees/slippage/latency), стресс-тесты, отчёты.

Model Training Service (RL/AI)

обучение/валидация, сохранение весов/чекпоинтов, метаданные.

Artifact Builder (ключевой)

выпуск deployable артефактов стратегий в immutable виде;

генерация manifest + SBOM;

подпись артефакта;

сохранение provenance (какая версия кода/данных/параметров).

Artifact Registry / Object Store

OCI registry (контейнеры) + object store (веса, отчёты, датасеты).

Agent/Device Registry

учёт агентов, публичные ключи, версии, attestation/health, привязка к workspace.

Control Plane

хранит desired state и очередь команд только жизненного цикла (request start/stop/pause/upgrade/config);

классификация изменений: TRADING_IMPACTING vs NON_IMPACTING.

Telemetry & Monitoring

ingestion телеметрии/логов/ивентов;

алерты; дашборды; экспорт отчётов.

Privacy & Governance Layer

data minimization, retention, RBAC, tenant isolation;

data residency (EU-region по умолчанию для EU клиентов);

экспорт/удаление/DSAR процессы.

Policy/Marketing Guardrails (не код, но процесс)

шаблоны сообщений в UI, чтобы не звучать как advice или “мы торгуем за вас”;

контроль текста лендингов/онбординга/писем.

Agent (local/VPS/on-prem) — “Execution runtime + Secrets + Risk + Journal”

Компоненты:

Agent Daemon

всегда работает (systemd/docker);

регистрируется в cloud;

принимает lifecycle requests;

тянет артефакты;

запускает runs;

шлёт телеметрию.

Local Vault (Secrets Store)

ключи брокера/биржи и любые секреты только локально;

шифрование (OS keychain / encrypted file);

ротация ключей локально;

жёсткое secret-redaction в логах до отправки телеметрии.

Strategy Runner

запускает стратегию изолированно (процесс/контейнер);

предоставляет унифицированный интерфейс snapshot -> intent;

обеспечивает лимиты ресурсов.

Broker Connectors (live trading clients)

только в агенте (в cloud вообще отсутствуют);

адаптеры IB/Alpaca/… и т.д.

Risk Manager + Kill Switch (локально, enforce)

pre-trade controls, rate limits, exposure/drawdown caps, circuit breakers;

локальная политика — приоритетнее любых “suggested” из cloud.

State Reconciler

консистентность позиций/ордеров;

idempotency keys;

восстановление после дисконнекта/рестарта.

Telemetry Buffer / Local Journal

durable очередь событий;

локальный журнал решений/инцидентов;

режим “degraded safe”: при потере критичных данных/связи — halt.

Approval UI (локально)

подтверждения TRADING_IMPACTING запросов (start/upgrade/config changes);

журнал кто подтвердил и когда.

2) Артефакт стратегии: Deployable Unit (чтобы не было “мы запускаем ноутбук”)
2.1 Strategy Manifest (контракт cloud↔agent)

manifest.json/yaml:

strategy_id, version, git_sha

entrypoint

runtime (python ver, cpu/cuda)

dependencies_lock_digest

model_artifacts (refs + digests)

data_contract (features/timeframes)

telemetry_schema_version

permissions (fs/network ограничения)

risk_profile_suggested (только suggested)

live_capabilities (needs broker access, etc.)

provenance (кто/что/когда собрал)

change_class (TRADING_IMPACTING/NON)

2.2 Immutable build + подпись + SBOM

Artifact Builder:

собирает артефакт (OCI image или пакеты);

фиксирует зависимости (lockfile);

генерирует SBOM;

подписывает релиз (подпись обязательна);

публикует digest.

Agent:

принимает только доверенный registry allowlist;

проверяет подпись и digest перед запуском.

2.3 “No silent upgrades” для trading-impacting

Любой апгрейд артефакта, влияющий на торговлю:

требует локального approve;

логируется как изменение прод-контуров (кто запросил, кто подтвердил).

3) Потоки: от Research до Live — пошагово
Шаг A — Research / Validate / Stress-test / Sim (cloud)

Задача: мощная лаборатория без превращения в “advice/execution”.

Пользователь пишет стратегию/модель (IDE/ноутбуки).

Прогоняет:

backtest,

симуляцию исполнения (fees/slippage/latency),

стресс-тесты (режимы рынка),

риск-репорты.

Cloud хранит:

отчёты, метрики, артефакты обучения, версии.

UI/формулировки:

метрики и сравнения, но без “вам надо купить X”;

любые “сигналы” маркировать как output пользовательской стратегии;

избегать персонализации под пользователя (если вы не в regulated advice).

Шаг B — Deploy to Agent (cloud кнопка “Deploy”, но через request/approve)

Пользователь выбирает:

target agent (его устройство/VPS/on-prem),

broker adapter,

режим (paper/live),

параметры мониторинга,

risk policy template (но enforce будет локально),

расписание.

Процесс:

Artifact Builder создаёт Build #N

immutable, signed, digest pinned.

Control Plane создаёт Deployment:

deployment_id

artifact_ref (digest)

desired_state = REQUEST_START (не RUNNING)

runtime_config (без секретов)

change_class = TRADING_IMPACTING

risk_profile_suggested_hash

Cloud отправляет агенту “deployment available”:

это request, не команда “торгуй”.

Шаг C — Setup Agent (у пользователя, один раз)
C1) Установка

daemon (systemd/docker);

BYO host / customer-managed.

C2) Регистрация

onboarding token с коротким TTL;

агент генерирует device keypair локально, регистрирует public key в cloud;

cloud фиксирует agent_id и политику доверия.

C3) Подключение брокера (секреты локально)

локальный UI: ввод ключей;

хранение в Local Vault;

cloud видит только health/connected, masked metadata;

телеметрия проходит через secret-redaction.

Шаг D — Live Run (agent 24/7)
D0) Локальное подтверждение trading-impacting действий

На REQUEST_START, REQUEST_UPGRADE, REQUEST_CONFIG_CHANGE(TRADING_IMPACTING):

агент показывает diff: что меняется, какие инструменты/лимиты/режим;

пользователь подтверждает локально (или есть заранее заданная локальная политика авто-approve для конкретного workspace/стратегии/инструментов).

Это ключевой guardrail против трактовки “облако управляет торговлей”.

D1) Pre-flight проверки

verify signature + digest;

verify manifest schema;

verify broker connectivity;

verify local policy firewall (локальные лимиты);

verify time sync;

verify “no cloud order payload” (на уровне протокола/типов команд).

D2) Запуск в изоляции

каждый run — отдельный контейнер/процесс;

лимиты CPU/RAM;

(enterprise) сеть egress allowlist, fs restrictions.

D3) Market data и state

данные берутся локально (от брокера/разрешённого источника);

state ведётся локально: позиции, ордера, fills.

D4) Где рождается live intent

Только локально.

стратегия получает snapshot;

вычисляет intent (target_position, desired exposure, etc.);

intent никогда не приходит из cloud.

D5) Risk Manager: intent → допустимые ордера (enforce)

проверка инструментов/экспозиции/плеча;

max order size/частоты;

max daily loss;

sanity checks по цене/спреду;

circuit breakers;

rate-limits.

Только после allow:

execution engine формирует ордера;

broker connector отправляет.

D6) Kill Switch (локально)

cancel open orders;

optional flatten — по локальной политике (не облако);

перевод в HALTED;

отправка телеметрии о причине.

D7) Reconciliation / Recovery

периодическая сверка с брокером;

idempotency keys / client order ids;

предотвращение дублей при рестартах;

при сомнениях — fail-safe halt.

D8) Безопасные режимы деградации

потеря связи с cloud: торговля может продолжаться, но с локальными safety guards;

потеря market data/качества данных: halt;

превышение ошибок брокера: halt;

подозрение на рассинхрон: halt.

Шаг E — Cloud Control & Monitoring (наблюдение + lifecycle requests)
E1) Что cloud показывает

online/offline агент;

requested/running/paused/halted/stopped;

PnL/позиции/экспозиции (в зависимости от consent и режима);

события ордеров/филлов (лучше агрегировано по умолчанию для privacy);

риск-метрики;

алерты.

E2) Команды cloud (строго “request”, без trading payload)

Safe list:

REQUEST_START_RUN(deployment_id) → локальный approve по умолчанию

REQUEST_STOP_RUN(deployment_id) → можно без approve

REQUEST_PAUSE_RUN(deployment_id) → можно без approve

REQUEST_UPGRADE_ARTIFACT(deployment_id, artifact_ref) → TRADING_IMPACTING → approve

REQUEST_UPDATE_CONFIG(deployment_id, config_blob)

TRADING_IMPACTING → approve

NON_IMPACTING → auto-apply возможно

REQUEST_ROTATE_AGENT_SESSION (security ops)

REQUEST_EXPORT_LOGS (с redaction)

E3) Команды cloud, которые запрещены

PLACE_ORDER, SUBMIT_ORDER, EXECUTE_SIGNAL

SET_TARGET_POSITION_NOW

любая “команда сделки”

E4) Neutralize “control plane = trading lever”

cloud не может поднять риски выше локальных лимитов (policy firewall);

нет silent updates для trading-impacting;

audit trail: кто запросил, кто подтвердил, какие diffs.

4) Как это ложится на твою текущую архитектуру (конкретно)

Ты уже имеешь: Python-модули, DI/YAML, connectors, risk, backtest, sim.

Тебе нужно сделать жёсткое разделение пакетов/дистрибутивов:

4.1 Два рантайма: research_runner и live_runner

research_runner (cloud): backtest/sim/training, без broker submitter

live_runner (agent): execution loop + broker connectors

Критическое правило сборки:
cloud-образы не содержат broker trading client libs.
Это проверяется CI (static check): “в cloud build нет импортов/зависимостей broker submitter”.

4.2 Единый Strategy API

стратегия выдаёт Intent

в cloud intent обрабатывает SimExecutionEngine

в agent intent обрабатывает LiveExecutionEngine + Risk Manager (enforce)

4.3 Протокол команд и типы изменений

типы команд строго перечислены и версионируются;

любые команды с payload, похожим на ордер, запрещены на уровне схемы (и CI).

6.1 Data minimization и уровни телеметрии

По умолчанию:

6.2 Data residency

EU-регион по умолчанию для EU клиентов;

enterprise: on-prem режим “telemetry stays local” (или выборочно).

6.3 RBAC / access controls / break-glass

доступ к торговым данным строго по ролям;

audit log доступа;

break-glass только для инцидентов.

6.4 Retention + DSAR

сроки хранения;

удаление по запросу;

экспорт данных пользователя.

7) Enterprise readiness: DORA / outsourced algo tooling / audits
7.1 DORA vendor pack

контракты: права аудита/инспекции, SLA, инциденты, субподрядчики, локации данных, exit plan;

evidence pack: экспорт логов, change management, vulnerability management, SBOM, incident runbooks.

7.2 Algo trading compliance support (не “мы compliant”, а “мы даём инструменты”)

kill switch, лимиты, тестовые режимы, логирование, time-sync;

клиент остаётся ответственным, вы — поставщик инструментария.

8) AI Act posture (чтобы маркетинг не загнал в худший периметр)
8.1 Роли и ответственность

вы предоставляете платформу/инфраструктуру;

модели могут быть пользовательскими;

provenance: версии моделей/данных/конфигов;

enterprise governance опции.

8.2 “Intended purpose” — контролируйте формулировки

не обещать применение в high-risk областях, если не готовы;

AI governance как “tooling”, не как “мы принимаем решения за вас”.

9) Надёжность и ответственность (чтобы претензии не убили)
9.1 Безопасные дефолты

paper-first;

лимиты по умолчанию;

авто-halt при сомнительных условиях.

9.2 Incident playbooks

что происходит при broker errors/latency spikes/data loss;

как пользователь видит и подтверждает восстановление;

как вы поддерживаете расследование без доступа к секретам.

9.3 Не обещать доходность

никаких “guaranteed returns”;

бэктесты с дисклеймерами.

10) ToS / Marketing / AUP / IP (это часть архитектуры, потому что продаёт смысл)
10.1 ToS (публичные)

“не инвестиционная консультация”;

“мы не брокер/не кастодиан/не исполняем и не передаём ордера от имени клиента”;

“исполнение — в среде пользователя/клиента”;

“пользователь ответственен за мониторинг/риск/соответствие правилам брокера”.

10.2 Marketing (что говорить и чего НЕ говорить)

Говорить:

“platform for research, simulation, and customer-controlled deployment”

“deploy to your own agent / your infrastructure”

Не говорить:

“we trade for you”

“auto-execution in our cloud”

“guaranteed profit”

10.3 AUP (acceptable use policy)

запрет манипуляций/market abuse/спама ордерами;

запрет нарушений правил площадок;

право ограничить/приостановить доступ (особенно cloud compute).

10.4 IP и данные клиента

стратегия/модель/логи принадлежат клиенту;

“мы не используем ваши стратегии/сделки для обучения” по умолчанию;

opt-in для улучшения.

12) UX сценарий (как это выглядит у пользователя, без “мы торгуем за вас”)

Research в cloud: стратегии, бэктесты, симуляции, отчёты.

Deploy в cloud: “Deploy to your Agent”.

Agent получает REQUEST_START и показывает локально:

что стартует, какие инструменты, какие лимиты, что изменилось.

Пользователь подтверждает локально (или заранее настроил локальную политику).

Live идёт локально 24/7.

Cloud — мониторинг и lifecycle requests:

stop/pause,

request upgrade (с локальным approve),

алерты/отчёты.

13) Как не “случайно” превратить cloud в execution service (финальная фиксация)

Никаких секретов в cloud (и контроль/сканеры).

Никаких live trading instructions из cloud (ни intents, ни targets, ни orders).

Control plane = lifecycle requests, а всё trading-impacting требует локального approve + policy firewall в агенте.

Никаких silent upgrades trading-impacting.

Маркетинг и ToS не противоречат архитектуре (иначе вас разнесут быстрее, чем код).
