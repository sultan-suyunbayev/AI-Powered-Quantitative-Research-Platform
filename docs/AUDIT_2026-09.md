# Repository audit — September 2026

Scope: the full tracked tree at `main@d1f5881` — 1 785 commits, 3 454 tracked files, ~50 MB
on GitHub. Purpose: prepare the repository for a public Apache-2.0 release (v1.0.0).

Severity: **P0** blocks the release · **P1** should be fixed before it · **P2** cosmetic.
Status is what actually happened on the `cleanup/public-release` branch.

The short version: nothing was leaking secrets, and the code is real. What was broken was
everything around it — the licence said proprietary, the dependency locks could not be
installed, so CI had been red for months and every quality tool in it was failing to run
rather than passing. Once they ran, they found things.

### 9.18 — the Windows column

CI builds and tests on `windows-latest` as well as `ubuntu-latest`, and once the suite ran
to the end there, a column of failures appeared that had nothing to do with the tests. The
services layer had never been executed on Windows. None of these is exotic; each is a POSIX
assumption written down as if it were portable.

| # | Finding | Sev | Status |
|---|---------|-----|--------|
| 9.19 | **Trading state could not be persisted at all.** `state_storage._file_lock` does `import fcntl` unguarded — there is no `fcntl` on Windows, so `save_state()` raised `ModuleNotFoundError` before writing a byte. Behind it, `JsonStateBackend.save` fsyncs the containing directory through `os.open(parent, os.O_DIRECTORY)`; `os.O_DIRECTORY` does not exist on Windows and the resulting `AttributeError` is not an `OSError`, so it escaped the `suppress(OSError)` meant to make that step best-effort and took the whole save down with it. | **P0** | **Fixed** — `msvcrt.locking` provides the exclusive lock where `fcntl` is absent, and the directory fsync is skipped where the flag does not exist. |
| 9.20 | **`flush_fsync` could not flush.** `atomic_write_with_retry(path, None)` opens the file `O_RDONLY` and calls `os.fsync`. ### 14.1 — the variance that never saw a second step

`VarianceGradientScaler` took each parameter's spatial mean and spatial mean-of-squares
*before* the exponential moving average, so `Var = E[g²] − E[g]²` measured how much a
gradient varies across a parameter's elements, not how much it varies between steps.
Feed it the same gradient forever and it reported a large variance.

Writing the two moments out separates them. Let `m_j` be element `j`'s temporal mean and
`v_j` its temporal variance. What the code computed was

    S − (mean_j m_j)²  =  mean_j(v_j) + Var_spatial(m)

The second term is the spatial spread of the per-element means. It is not stochastic
noise and it does not vanish when the gradient is constant, which is exactly what the
two `xfail` tests were catching. The statistic that was wanted is `mean_j(v_j)`, and

    mean_j(v_j) = S − mean_j(m_j²)

so the first moment has to be kept per element and squared *before* averaging. The
second moment can stay scalar: an EMA is linear, so `EMA[mean(g²)]` already equals
`mean_j(E[g_j²])` exactly. Jensen gives `mean_j(m_j²) ≤ S`, so the corrected quantity is
non-negative by construction.

That left a numerical problem underneath the statistical one. When the gradient does not
vary in time the two terms are equal to the last bit, and in float32 their difference is
all rounding residue — about 1e-7 relative. The normalisation then divides by the squared
spatial mean, which clamps to 1e-12 for a gradient centred on zero, and 1e-7 over 1e-12 is
a variance of 1e5 where the answer is 0. The difference is taken in float64 now, and a gap
smaller than the relative precision the float32 operands actually carry is reported as
zero, because that is what it is. The normalisation itself is untouched: `alpha` and
`variance_cap` are calibrated against it.

Checkpoints: `state_dict` writes version 4.0 and carries the elementwise first moment. A
3.1 or 3.2 checkpoint still loads — every element is seeded with the scalar it does carry,
which is exact where the gradient is spatially uniform and approximate otherwise — and it
warns rather than implying the load was lossless. 363 VGS tests pass.

### 14.6 — seven minutes, and what they were actually spent on

A profile of the offline path answered this in one line: 1 384 409 calls to a nested
`_calc_ema` for 1200 bars, 83% of the runtime. The MACD block read:

    macd_list = []
    for length in range(26, len(seq) + 1):
        sub_seq = seq[:length]
        e12 = _calc_ema(sub_seq, 12)
        e26 = _calc_ema(sub_seq, 26)

For every prefix of the price history it recomputed both exponential moving averages from
the first element — Θ(n²) per bar, Θ(n³) over a run — to produce a list whose last entry
is the only one MACD needs and whose earlier entries the previous bar had already
computed. `seq` is as long as the longest configured window, 10 080 bars for the default
CVD windows, so in the live update path that is on the order of 200 million float
operations per bar.

An EMA is a recursion, so the whole series comes out in one pass: seed each average the
way `_calc_ema` seeds it, with the mean of its first n values, then fold in one price at a
time. Same operations in the same order, so the same floats — checked bit-for-bit against
the old loop over 203 cases with lengths from 0 to 3000, not merely "close".

Two smaller things came out of the same profile. `calculate_garch_volatility` fits on
`prices[-min(n, len):]`, so while the history is shorter than the window every configured
window sees the same prices and returns the same number: three identical
maximum-likelihood fits per bar, and a run is in warm-up for its first month on the
default windows. It is fitted once per distinct effective window now. And `test_cvd.py`
asked for a `FeatureSpec` without volatility windows, so it got the defaults — three
GARCH models refitted on every one of its bars, for a file whose every assertion is about
`cvd_*`. It names the families it tests.

**377 s to 6.2 s.** The GARCH refit itself is left alone and recorded below.

### 14.7 — checking the buffer at the door

`obs_builder` is compiled with `boundscheck=False` and writes the whole observation
through typed memoryviews. That is deliberate — it runs on every environment step — but it
means a caller who sizes the buffer by hand and gets it wrong writes past the end of
somebody else's array and nothing raises. §10.29 was exactly that: the probe used a
21-wide external block while the mediator had grown to 35, and every step wrote 31 floats
past the end of the observation.

Turning bounds checking on would cost that hot path for a check whose answer is the same
on every iteration. Instead the contract is enforced where it can be checked once:
`required_feature_count()` computes the length the arguments imply, and the Python-callable
entry point refuses a buffer that cannot hold it, and a validity array shorter than the
values it is indexed alongside. The `nogil` core is untouched, and so is its speed.
`test_all_feature_counts_agree` now also pins that arithmetic against the runtime probe, so
a new block cannot be added to the builder without the mismatch being caught.

### 14.8 — the LOB call that was not missing anything

`run_full_step_logic_cython` called `lob_clone.match_market_order_cy(…, offsets,
fully_executed_ids)`. `fast_lob.CythonLOB` has `match_market_order(…, out_is_buy,
out_is_self, max_len)`: no write offset, no timestamps, no fully-executed list. §9.16
called the gap "missing matching semantics". It is not missing, it is unreported:

- **Offsets** — the C++ side always writes from index 0. The trades are taken into scratch
  buffers and copied to their place, which is needed anyway: the workspace keeps maker ids
  as `unsigned long long` and the flags as `char`, while the C++ signature writes
  `long long` and `int`.
- **Timestamps** — every trade of one market event carries the timestamp the caller handed
  to the match. The caller fills that column itself, exactly as it already fills
  `is_buy_side` and `taker_is_agent`.
- **Fully-executed ids** — `OrderBook::_match_logic` pops a maker and erases its index
  entry precisely when the fill consumed it whole; it counts them and returns the count,
  which `match_market_order` discards. So "the match consumed this order whole" is the same
  statement as "the order is no longer in the book", and `contains_order` answers it.
  Self-trade prevention also pops a maker, but records no trade, so those ids never enter
  the trade list and cannot be mistaken for fills.

The workspace takes its capacity as a constructor argument while the module hardcodes
`MAX_TRADES_PER_STEP = 10000`, so the limit comes from the buffers themselves, and
`max_len` is one past the room left — a match that would overflow reports one trade too
many and raises, instead of truncating a step's trades in silence.

Past the `AttributeError`, the test that reaches this found a second thing. It asserted
`rel=1e-12` on `state.cash`, `state.units` and `state.net_worth`, which `EnvState` keeps as
`cdef public float`: 32 bits, an epsilon of 1.2e-7. Those assertions had never run, so the
tolerance had never been true of anything. A single store rounds by up to half an ULP,
6e-5 at a cash of about 1120, and that was the whole of the disagreement. The bar is the
storage type's.

`tests/test_reward_penalty_stability.py` was also skipping itself away: it imported
`SimulationWorkspace` and `CythonLOB` from `lob_state_cython`, which cimports them but does
not re-export them, so the `ImportError` skipped the module and nothing in it had ever run.
They come from `coreworkspace` and `fast_lob`.

### 14.9 — a directory and a file are different things

`BuildResult.artifact_path` is the bundle *directory* — artifact, manifest and SBOM live in
it, and a passing test pins that. `ArtifactPublisher.publish()` takes the artifact *file*:
it hashes it and compares against `manifest.artifact_digest`, which the builder computed
over that same file. Both are right. The result simply never said where the file was, so
`publish(result.artifact_path, …)` opened a directory.

The seam was an omission, not a conflict, and picking a side was never necessary.
`BuildResult` has `artifact_file`, the path `build()` already had in hand;
`artifact_path` keeps its meaning. A test builds and publishes end to end and checks that
the digest the publisher recomputed is the one the builder signed.

### 14.10 — SA-PPO, and what "robust KL" means

The entry said the sample mask and the recurrent state disagree about which axis they
index. They do, in two places, and there were two further defects behind that.

**The axis.** A recurrent policy's state is `[n_layers, n_seq, hidden]`; its second axis
counts sequences, the clean/adversarial split counts samples. `tuple(s[:, ~adv_mask] …)` in
the trainer and `tuple(s[:, num_clean:] …)` in the wrapper line up only when a minibatch
holds one step per sequence. The state is not split any more: where one is present, the
policy runs over the whole minibatch and the adversarial rows are read back afterwards, on
the batch axis alone. That is also what a recurrent policy needs, since a row's hidden
state depends on the rows before it. A feedforward policy treats rows independently, so
that path keeps the cheaper slice and its numbers are unchanged.

**The pairing.** The trainer asked for `KL(π(·|s_clean) ‖ π(·|s_adv))` between *different
samples*: `observations[~mask]` against `augmented[mask]`, different sizes, different rows.
SA-PPO's regulariser (Zhang et al., 2020) is `E_s[KL(π(·|s) ‖ π(·|s+δ))]` — one state, one
perturbation of it. Between two disjoint sets of examples that quantity is not a divergence
of anything. Both sides get the whole minibatch now and the mask selects the perturbed rows
out of the per-sample KL. `compute_adversarial_loss` had always done it this way; the newer
path had not.

**The gradient.** `compute_robust_kl_penalty` returns a float, and the trainer wrapped it
in `policy_loss.new_tensor(...)`. A constant has no gradient, so the penalty moved the
number that got logged and left the update exactly as it was — the regulariser did not
regularise. The float signature is public and stays; `compute_robust_kl_penalty_tensor`
returns the same value attached to the graph, and the trainer prefers it when the wrapper
offers it.

Two smaller things in the same code. The analytical KL branch averaged over event
dimensions where the KL of a factorised distribution is their *sum*, so it disagreed with
its own Monte Carlo fallback by a factor of the action dimension; event dimensions are
summed now. And the trainer logged the result with `self.logger.record(key, float(value))`,
which raises on the `sa_ppo/kl_method` string the moment that path is reached — so the
block would have failed on the line after the one that used to crash.

### 14.11 — found on the way, and left open

- **`calculate_garch_volatility` refits a GARCH(1,1) by maximum likelihood on every bar,
  for every window.** Deduplicating identical fits helps during warm-up, which is most of a
  backtest, but in steady state it is still one full fit per window per bar. The standard
  treatment is to refit periodically and propagate `σ²_t = ω + α ε²_{t−1} + β σ²_{t−1}`
  with the fitted parameters between refits, which is O(1) per bar — and which changes the
  numbers a live model sees between refits. That is a modelling decision, not a cleanup, so
  it is named rather than made.
- **`ViolationType.INVALID_LEVEL` is declared and never raised.** The telemetry middleware
  does not validate the level; the router does, one layer in. Either the member is dead or
  the check is missing, and which one is a product decision.
